TASK: Create the HoneyDoo starter application

Implement the project in the current HoneyDoo workspace. Do not stop at an implementation plan. This is a small, runnable first increment, not the complete household-management application.

CONTEXT AND SCOPE
HoneyDoo is a responsive household task-management web application being developed by Fourward Solutions for Purdue Global IT488, Group 3. The planned stack is C#, ASP.NET Core Razor Pages, and SQLite. This task implements the branded welcome screen, team information, project structure, and setup documentation only.

The instructor has confirmed that Unit 1 does not require a functioning application, completed database, virtual machine, or shared hosting. This starter is useful preparation beyond that minimum; do not describe unfinished features as implemented.

FIRST: INSPECT AND PROTECT THE WORKSPACE
- Inspect existing files, repository instructions, git status, and available .NET SDKs before making changes.
- Work only in the intended HoneyDoo workspace. Do not modify another project or overwrite teammates' work.
- Target .NET 10 LTS (net10.0), using compatible stable dependencies. Do not silently substitute another framework or an unsupported .NET version.
- If required tooling is unavailable, complete the files that can be created reliably, document the blocker, and clearly distinguish untested work. Do not claim a successful build or invent test results.
- Do not create a remote repository, push, merge, deploy publicly, purchase hosting, or choose a software license. Leave existing repository policies intact.

1. PROJECT FOUNDATION
Create a normal ASP.NET Core Razor Pages solution, not a standalone HTML mockup.

Use a single web project with clearly named folders for presentation, future business logic, and future data access. Add small explanatory README files to reserved folders when useful; do not invent unnecessary classes, interfaces, or services merely to fill them.

SQLite remains the planned database. Do NOT create household/user/task tables, authentication, Entity Framework migrations, or a fake database-connected indicator in this task. The welcome screen must run without a database. Explicitly document data access as future work for team review.

Do not introduce React, Angular, Blazor, MAUI, microservices, Docker, a separate API, or a required Node/npm build process. Keep dependencies minimal and the code understandable to students learning ASP.NET Core.

2. BRAND AND VISUAL DESIGN
Product name: HoneyDoo
Tagline: One home. One list. Less stress.
Development team: Fourward Solutions

Design a clean, welcoming, mobile-first interface that feels like an intentional product rather than the unmodified ASP.NET template.

Use warm off-white backgrounds, dark green primary elements, restrained honey-gold accents, readable dark text, generous spacing, and softly rounded panels. Use a system-font stack and local assets; no remote font or icon dependencies.

Create an original, simple SVG brand mark combining a house outline and checkmark, optionally framed by a subtle honeycomb shape. Keep it legible at small sizes. Store it as honeydoo-mark.svg and provide a matching SVG favicon. Display the word HoneyDoo as actual text beside the mark. Do not copy existing product or university logos, or imply university endorsement.

5. ABOUT PAGE AND ACCESSIBILITY
Create /About with a brief explanation of the project, its current starter scope, the planned stack, and a section with id="team" listing the four members.

Store repeated team information in one simple shared model/configuration source, or a shared partial, so names do not drift between pages. Avoid unnecessary abstraction.

Use semantic HTML, one main heading per page, a skip-to-content link, visible keyboard-focus styles, accessible link names, meaningful alt text where appropriate, and decorative icons hidden from screen readers. Ensure readable contrast and comfortable touch targets.
